## 二、本次已复现并修复

以下 6 项新回归测试先在 v4 失败，再在修订版通过。

1. 调用参数与计量可被后续修改：记录器原先保留调用方对象引用，调用中改模型或调用后改 Token 会污染账本。现在在入口校验并复制元信息、在响应边界校验并复制计量。
2. 超过单任务 1000 次调用才写入失败：原先可能已完成第 1001 次收费调用，finish 才因账本上限失败。现在在调用前预占记录名额，包含同时进行的调用，超限不执行 operation。
3. 非法计量阻塞整个任务保存：例如负 Token 原先会在 finish 阶段使整条记录无效。现在保留已完成调用，计量标为未知，抛出 TASK_MEASUREMENT_INVALID，提示修正适配器而非重跑收费调用。
4. 存储方可改坏重试记录：原先把内部最终对象直接交给存储接口。现在提交副本，即使存储失败且改动入参，也保留相同内容供重试。
5. 综合推荐的畸形资源可抛错：非列表资源、额度窗口中含 null 等原先可能直接异常。现在返回 invalid / unavailable 及缺失信息，不产生可执行建议。
6. 两套时间评估的截止边界不同：独立时间建议把“恰好等于截止时间（已含余量）”判作来不及，而综合推荐接受。现在统一接受相等边界；无效当前时间也会拒绝。

相关代码：src/history/TaskExecutionRecorder.ts、electron/taskLedgerSchema.ts、src/reports/unifiedPlanner.ts、src/reports/taskAdvisor.ts。未增加自动调用权限，也未改变真实 / 模拟账号隔离。

## 三、同类工具值得借鉴什么

比较对象是功能相邻工具，不是要求桌宠复制大型服务端平台。下列是官方已公开的能力；“PetCast 建议”是本次设计判断，不是对方官方结论。

| 工具与官方依据 | 值得借鉴的能力 | PetCast 的具体缺口 |
| --- | --- | --- |
| [Langfuse 质量评分](https://langfuse.com/docs/evaluation/scores/overview) | 可将人工、程序或用户反馈的评价挂到已有任务轨迹，事后补充评分 | 当前 evaluation 嵌在不可变完成记录中，无法自然地在用户看完结果后补评 |
| [Langfuse Token 与成本](https://langfuse.com/docs/observability/features/token-and-cost-tracking) | 区分服务商提供的计量与基于模型定义的费用推算，明确缓存 / 推理细分口径 | 当前可保存估算金额，但没有价格来源 / 生效时间；预算模式要求实报费用，只有 Token 时可能一直无法生成费用方案 |
| [Helicone 会话追踪](https://docs.helicone.ai/features/sessions) 与 [属性筛选](https://docs.helicone.ai/features/advanced-usage/custom-properties) | 将相关请求分组，展示父子层级，并按属性检索 | 当前只有任务→调用两层列表，超过 100 个任务只展开最近 100 个，缺少搜索 / 分页与项目维度 |
| [LiteLLM 路由](https://docs.litellm.ai/docs/routing) 与 [预算 / 限流](https://docs.litellm.ai/docs/proxy/users) | 执行链路处理超时、重试、故障冷却及资源限制 | 当前 D 只给建议，尚无真实健康状态、执行时限额或多任务资源预留，不能保证不超预算 |

接入这些产品并非必要条件；首版可以在本地实现小而明确的对应能力。未来若与 Langfuse 交换数据，必须注意其非重叠 Token 分桶和 PetCast 输入含缓存的口径不同，不能直接逐字段相加。

## 四、后续改进顺序（尚未实现）

### P1：先保证真实使用时能形成可靠建议

1. **接通真实执行与事后评价。** 执行完成立即保存计量；评价作为单独、可追溯的事件追加，带 taskId、评价时间、评价者类型、标准版本及修订关系，禁止改写旧调用账单。界面提供“达标 / 需修改 / 无法判断”。只将同一评价标准的结果用于比较。验收：重启后可给已有任务补评，重复提交不重复计数，切换账号不串记录。
2. **分开报表区间与推荐样本区间。** 当前 planner 接收到的是所选报告 tasks，所以新一周或选短区间会样本不足。推荐应默认查询独立的近 30 / 90 天记录，标明实际样本范围与数量；报表仍按用户选定周期统计。验收：切换本周 / 本月不应无解释地改变同一待办的候选；账号切换立即撤掉旧样本。
3. **补齐候选能力与任务条件。** 需要工具调用、图片、上下文长度等要求应由任务分析提供，并与候选能力配置匹配；先过滤不兼容模型。当前只靠可比任务组和手动访问确认，不能宣称已自动验证全部能力。验收：不支持必要能力的低价模型不得因更便宜排第一。
4. **让费用估算可用且可审计。** 保留“实际计量”和“价格估算”两个来源；为估算记录价格版本、生效时间、币种、缓存 / 推理计费口径。用户明确选择允许估算时，才给带估算标记的预算参考，不能显示成实付费用。验收：价格缺失 / 过期说明原因；换价格版本不改历史实报账单。
5. **自动执行前补执行层控制。** 任务队列需要预算预留、实际结算、失败释放、并发上限、取消和超时，以及有界重试和故障冷却。多任务不能各自把同一份余额当成可用。D 的 P80 历史估计不构成费用硬上限。验收：两个并发任务不能重复占用同一预算；单次重试有记录且次数有上限。

### P2：让建议可验证、报告更好用

- 建议生成时保存一个版本化快照，关联待办 ID、候选、证据、规则版本；记录采纳 / 忽略和实际完成结果。之后展示预计与实际耗时 / 消耗偏差、达标情况，验证规则是否有效。不能把“采纳建议”直接称为节省了多少钱。
- 目前每模型至少 3 条且所有已评价记录达标，一次失败可能在所选最近 90 天内一直排除模型。保留严格默认，同时设计近期窗口、质量覆盖率、失败原因分类和人工试用入口；阈值需真实数据校准，不直接把规则放宽成所谓“智能”。
- 明细增加日期、模型、任务类别、状态过滤，任务 ID 搜索与分页。高消耗条目应跳到对应调用，不要求用户在长列表里找；提供范围明确的 JSON / CSV 导出与数据覆盖说明。
- 增加父任务 / 子任务 / 步骤关联，区分排队时间、模型等待和实际执行时间；当前端到端耗时不能解释延迟发生在哪里。
- 保存时区偏好，突出“截至何时”和样本缺口；为跨午夜 / 周界 / 月界长期开启增加验收。提醒默认少打扰，避免把缺失记录当作用户不工作。
